1. Project Overview

Name: HospiTrack — Hospital Management System

Problem: Manual hospital work causes scheduling conflicts, lost records, and billing errors.

Solution: A web app with 3 portals — Admin, Doctor, Patient — each with role-specific features.

  • Centralizes hospital data in one database
  • Real-time appointment scheduling
  • Doctors access patient history instantly
  • Automated billing and invoice tracking

2. How To Use This Software

How to register an account?

1. Go to the Register page

2. Enter your full name, email, phone number, and password

3. Click Register — your account is created with role = PATIENT

4. You are redirected to the login page

How to log in?

1. Enter your email and password

2. Click Sign In

3. The system checks your role and redirects you to the right portal:

  • ADMIN → /admin/dashboard
  • DOCTOR → /doctor/dashboard
  • PATIENT → /patient/dashboard

How does a patient book an appointment?

1. Go to "Browse Doctors" page

2. Search by doctor name or specialty

3. Click on a doctor to see their details (fee, room, specialization)

4. Click Book → select a date from the calendar → pick an available time slot

5. Enter a reason for the visit (e.g., 'Fever', 'Checkup')

6. Click "Book Appointment" — status is set to PENDING

7. The appointment now appears in the admin's queue for approval

How does an admin assign a doctor to an appointment?

1. Go to "Appointments" page in the admin portal

2. See all appointments with PENDING status at the top

3. Click the Assign button on a pending appointment

4. Select a doctor from the dropdown (shows name, specialization, room)

5. Click "Assign" — the doctor is linked to the appointment

6. Click Confirm to change status from PENDING → CONFIRMED

7. The patient can now see the confirmed appointment in their dashboard

How to cancel an appointment?

1. Admin or Doctor can cancel from the Appointments page

2. Click the Cancel button on a PENDING or CONFIRMED appointment

3. Status changes to CANCELLED

4. Note: You cannot cancel a COMPLETED appointment

How does a doctor complete a consultation?

1. Go to "Appointments" in the doctor portal

2. Find the CONFIRMED appointment for today

3. Click 'Consult' to open the Consultation Modal

4. Fill in: diagnosis (required), vitals like BP/temperature (optional), notes (optional)

5. Add prescriptions: medication name, dosage, frequency, instructions

6. Click "Submit" — a MedicalRecord is created and appointment auto-changes to COMPLETED

How does a patient view their medical records?

1. Go to "Medical Records" in the patient portal

2. See a list of all past consultations

3. Click on a record to expand and see: diagnosis, vitals, notes, prescriptions

How does billing work?

1. Admin goes to "Billing" page and clicks "Create Invoice"

2. Select the patient, enter description and amount

3. Invoice number is auto-generated (INV-001, INV-002...)

4. Patient sees the invoice in their "Billing" page and clicks "Pay"

5. Select payment method (Card / Cash / Insurance)

6. Invoice status changes to PAID

How to manage departments?

1. Go to "Departments" in the admin portal

2. Click "Add Department" → enter name, select a head doctor, set location

3. Choose an icon and color for the department card

4. Click Save — department is created

5. Can also edit or delete departments from the list

How to manage hospital beds?

1. Go to "Beds" in the admin portal

2. See beds grouped by ward

3. Toggle bed status: Available ↔ Occupied

4. Click "Add Bed" to create a new bed with number, ward, and department

How does a doctor view their schedule?

1. Go to "Schedule" in the doctor portal

2. See a weekly calendar view with all appointments

3. Each appointment shows patient name, time slot, and status

How does search work?

1. Type a search query in the search bar

2. The system searches across patients, doctors, and appointments simultaneously

3. Results are grouped by type with counts (e.g., '3 patients, 2 doctors, 1 appointment')

3. Architecture

How It Works (8 steps)

  1. User opens site → sees login page
  2. Enters email + password → clicks Sign In
  3. Browser sends POST to /api/auth/login
  4. Server checks: email exists? password correct?
  5. If valid → creates JWT token → sets as httpOnly cookie
  6. Browser stores cookie → redirects to dashboard (admin/doctor/patient)
  7. User navigates → browser sends GET requests to API routes
  8. API queries PostgreSQL via Prisma → returns JSON → page updates

Server vs Client Components

Server Components (Layouts)

Run on server. Used for auth checks — wrong role = never see the page.

Client Components (Pages)

Run in browser with "use client". Handle forms, buttons, state.

5. Authentication & Security

Login Flow (7 steps)

  1. User enters email + password
  2. Zod validates client-side (email format, password length)
  3. POST to /api/auth/login
  4. Server finds user by email
  5. bcrypt compares password with stored hash
  6. If valid → creates JWT with { userId, email, role }
  7. Sets httpOnly cookie → browser sends it with every request

Security Measures

Password Hashing: bcrypt, 10 salt rounds. One-way — can't reverse.
httpOnly Cookie: JWT in cookie JS can't read. Prevents XSS.
Role Check: Layouts verify JWT role server-side. Wrong role → redirect.
Server Validation: validateBody() checks every API request.

8. Key Definitions

ORM — Interact with DB using code objects instead of raw SQL. (Prisma)
JWT — Token with user data (ID, email, role), signed with secret key.
httpOnly Cookie — Cookie JS can't access. Prevents XSS.
bcrypt — Password hashing. One-way: plain text → hash.
RBAC — Access based on role. Admin/Doctor/Patient see different pages.
CRUD — Create, Read, Update, Delete. Every resource supports all four.
API — Rules for software to communicate. Frontend ↔ Backend via REST.
SSR — Server renders page before sending. Faster load, allows auth checks.

9. Viva Q&A

Q1: What is this project?

HospiTrack — Hospital Management System with 3 portals: Admin manages ops, Doctor handles consultations, Patient books appointments and views records.

Q2: Why Next.js?

SSR for auth before page loads. App Router for file-based routing. Built-in API routes — no separate backend. One codebase for everything.

Q3: Why Prisma?

Type safety (errors at compile time). Declarative relations (no JOINs). Auto migrations — change schema, run prisma migrate.

Q4: How does auth work?

Login → bcrypt verifies → JWT with {userId, email, role} → httpOnly cookie → layouts call requireRole() to check JWT + role.

Q5: Server vs Client Components?

Server: runs on server, no hooks, auth checks. Client: runs in browser with "use client", handles forms/state.

Q6: How are passwords stored?

Hashed with bcrypt (10 salt rounds). One-way — can't reverse. Login compares entered password with stored hash.

Q7: Hardest part?

Appointment status state machine: PENDING → CONFIRMED → COMPLETED. Enforced in API + UI. Also: DB schema with proper relationships.

Q8: What to improve?

(1) Middleware API auth for all endpoints. (2) Real-time notifications via WebSockets. (3) Password reset with email.

10. Design Decisions

JWT cookies over sessions? Stateless — no session store. Scales easily. httpOnly prevents JS access (safer than localStorage).
Tailwind CSS? Rapid prototyping. Design system in config, applied everywhere. No CSS files.
Zod? Same validation client + server. Prevents bypassing client checks.
